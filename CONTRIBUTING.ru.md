# Гайд по контрибьютингу

Спасибо, что хотите помочь `tatarverse.cc` — открытому каталогу татарских,
башкирских, татаро-башкирских и крымскотатарских центров и сообществ.

Самый ценный вклад — это **проверенные данные**: новый центр, актуализация
контактов, английский перевод, ссылка на источник. Для такого вклада
**не нужно быть программистом** и не нужно ничего устанавливать.

| --- | --- |
| Исправить опечатку, ссылку, город, добавить один центр | [Правка через сайт GitHub](#для-новичков-правка-через-сайт-github) |
| Добавить несколько центров, перевод, поправить UI или код | [Форк и локальная разработка](#для-опытных-форк-и-локальная-разработка) |

## Для новичков: правка через сайт GitHub

Этот путь работает целиком в браузере. Git, терминал и Node.js не нужны.
Нужен только бесплатный аккаунт на [github.com](https://github.com).

### Шаг 1. Найдите нужный файл

Карточки центров лежат в
[`src/data/centers_formatted/`](https://github.com/proxima812/tatarverse/tree/main/src/data/centers_formatted).
Каждый файл — один центр, например `tbk-389.mdx`.

Как найти нужный центр быстрее: откройте папку на GitHub и нажмите `t` —
включится поиск по именам файлов. Если знаете только название центра,
воспользуйтесь поиском по репозиторию: в строке поиска GitHub введите название
и добавьте `path:src/data`.

### Шаг 2. Нажмите карандаш

В правом верхнем углу файла нажмите иконку карандаша
(**Edit this file**). GitHub автоматически создаст ваш форк — копию репозитория
в вашем аккаунте. Ничего дополнительно делать не нужно.

### Шаг 3. Внесите правку

Отредактируйте текст прямо в браузере. Соблюдайте
[общие правила](#общие-правила) и [схему полей](#схема-полей-центра).

Вкладка **Preview** покажет, как отрендерится Markdown.

### Шаг 4. Опишите изменение

Нажмите **Commit changes**. В открывшемся окне:

- В первую строку напишите короткое описание, например
  `fix(centers): обновлён Instagram центра в Караганде`.
- В поле описания добавьте **ссылку на источник** — это обязательно для
  фактических правок.
- Оставьте выбранным **Create a new branch for this commit and start a pull
  request**.

### Шаг 5. Откройте pull request

Нажмите **Propose changes**, затем **Create pull request**. Готово —
дальше см. [Ревью и что будет дальше](#ревью-и-что-будет-дальше).

Если после ревью попросят что-то поправить, откройте файл в своей ветке
(GitHub покажет ссылку в PR) и снова нажмите карандаш — новые коммиты
добавятся в тот же pull request автоматически.

## Для опытных: форк и локальная разработка

### Требования

- **Bun** 1.3 или новее — основной пакетный менеджер проекта
  ([установка](https://bun.sh/docs/installation)).
- **Node.js** 20 или новее — нужен для скрипта релизов и Wrangler.
- **Git**.

Проект работает на Astro 7 (статическая сборка), MDX content collections,
Tailwind CSS v4 и деплоится на Cloudflare Pages.

### Шаг 1. Форк

Откройте [репозиторий](https://github.com/proxima812/tatarverse) и нажмите
**Fork** в правом верхнем углу. Это создаст копию под вашим аккаунтом.

Через [GitHub CLI](https://cli.github.com) то же самое одной командой,
сразу с клонированием и настройкой `upstream`:

```bash
gh repo fork proxima812/tatarverse --clone
cd tatarverse
```

### Шаг 2. Клонирование и upstream

Если форкали через веб-интерфейс, клонируйте свой форк и добавьте ссылку на
исходный репозиторий как `upstream` — она нужна, чтобы потом подтягивать
свежие изменения:

```bash
git clone https://github.com/<ваш-логин>/tatarverse.git
cd tatarverse
git remote add upstream https://github.com/proxima812/tatarverse.git
git remote -v
```

После этого `origin` — ваш форк (туда пушите), `upstream` — исходный
репозиторий (оттуда тянете).

### Шаг 3. Зависимости и запуск

```bash
bun install
bun run dev
```

Сайт поднимется на `http://localhost:4321`.

Файл `.env` **не нужен** для работы с контентом, вёрсткой и переводами —
он требуется только для серверных функций приёма заявок (Telegram-бот и
Supabase) и содержит секреты, которых нет в репозитории. Локально формы
отправки просто не будут работать — это нормально и не мешает остальной
разработке.

### Шаг 4. Ветка под задачу

Не работайте в `main` своего форка — так проще синхронизироваться и вести
несколько правок параллельно:

```bash
git switch -c centers/karaganda-instagram
```

Понятные префиксы: `centers/`, `i18n/`, `ui/`, `docs/`, `fix/`.

### Шаг 5. Правки и проверка

Внесите изменения, затем прогоните [проверку](#проверка-перед-pr).

### Шаг 6. Коммит и пуш

```bash
git add src/data/centers_formatted/tbk-389.mdx
git commit -m "fix(centers): обновлён Instagram центра в Караганде"
git push -u origin centers/karaganda-instagram
```

В выводе `git push` будет ссылка на создание pull request.

> **Про хук `pre-push`.** В репозитории есть `.githooks/pre-push`, который
> автоматически поднимает версию релиза. Он предназначен для мейнтейнеров и
> **в форке его подключать не нужно** — по умолчанию он не активен. Если вы
> ранее включали `core.hooksPath` и он мешает пушу, используйте
> `RELEASE_BUMP_SKIP=1 git push`. Не поднимайте версию в `package.json`
> в своих PR — это делает мейнтейнер.

## Работа с ветками и синхронизация форка

Перед новой задачей подтяните свежий `main`, чтобы не разрешать лишние
конфликты:

```bash
git switch main
git fetch upstream
git merge --ff-only upstream/main
git push origin main
```

Если ваша ветка отстала от `main`, пока шло ревью:

```bash
git switch centers/karaganda-instagram
git fetch upstream
git rebase upstream/main
git push --force-with-lease
```

`--force-with-lease` безопаснее обычного `--force`: он не перезапишет чужие
коммиты, если в ветку кто-то успел что-то добавить.

## Оформление коммитов

Проект использует [Conventional Commits](https://www.conventionalcommits.org/ru/):

```txt
<тип>(<область>): <краткое описание>
```

Типы, которые применяются здесь: `feat`, `fix`, `docs`, `refactor`, `style`,
`chore`. Области — обычно `centers`, `i18n`, `ui`, `projects`.

```txt
feat(centers): добавлен центр в Актобе
fix(i18n): исправлен английский перевод фильтра категорий
docs(contributing): добавлена инструкция по форку
```

Описание можно писать на русском или английском. Тип и область — латиницей.

## Как открыть pull request

1. На странице своего форка или в выводе `git push` нажмите
   **Compare & pull request**.
2. Убедитесь, что база — `proxima812/tatarverse`, ветка `main`, а справа —
   ваша ветка.
3. Заголовок — в формате коммита (см. выше).
4. В описании укажите:
   - **что** изменилось и **почему**;
   - **ссылку на источник** для каждой фактической правки;
   - номер issue, если PR его закрывает, — строкой `Closes #12`.
5. Один PR — одна тема. Новый центр, правка данных, перевод и фикс UI должны
   идти отдельными PR: их проще ревьюить и откатывать.

Черновик всё ещё в работе? Откройте его как **Draft pull request**.

## Общие правила

- Один pull request на одну тему: новый центр, правка данных, перевод или
  небольшое исправление.
- Не форматируйте и не меняйте соседние файлы без необходимости.
- Для фактических правок добавляйте источник: сайт, соцсеть, официальный пост,
  страницу организации или другую проверяемую ссылку.
- Если данных нет, не пишите заглушки вроде `неизвестно`, `n/a`, `-`.
  Лучше пропустить поле.
- Сохраняйте нейтральный тон: без рекламы, оценок и неподтверждённых
  формулировок.
- Не меняйте `tbk-*` имена файлов: они работают как публичные стабильные slug,
  и переименование ломает внешние ссылки и SEO.
- Не коммитьте `dist/`, `.astro/`, `node_modules/`, `.env` — они в `.gitignore`.
- Не добавляйте зависимости без обсуждения в issue.

### Про личные данные

Публикуйте только **публичные** контакты организаций: сайт, соцсети,
рабочую почту, публичный телефон центра. Не добавляйте личные телефоны,
домашние адреса и приватные контакты людей, даже если они вам известны.
Имя руководителя можно указывать, если оно уже опубликовано официально.

## Где лежат данные центров

Русские карточки центров (исходная версия):

```txt
src/data/centers_formatted/
```

Английские переводы центров:

```txt
src/data/centers_i18n/en/
```

Имена файлов должны совпадать между версиями:

```txt
src/data/centers_formatted/tbk-366.mdx
src/data/centers_i18n/en/tbk-366.mdx
```

Русская версия — исходная. Если меняете её, проверьте, нужна ли такая же
фактическая правка в английском переводе. Английский перевод не обязателен для
нового центра, но приветствуется: сейчас переведены не все карточки.

Обе директории читаются через `glob`-загрузчики коллекций `centers` и
`centersEn` в [`src/content.config.ts`](./src/content.config.ts).

## Как добавить новый центр

1. Найдите следующий свободный `tbk-*` номер:

   ```bash
   ls src/data/centers_formatted | sort -V | tail -1
   ```

   Через веб-интерфейс — просто откройте папку, файлы отсортированы.

2. Создайте `.mdx` файл с этим номером в `src/data/centers_formatted/`.
3. Заполните frontmatter по [схеме](#схема-полей-центра).
4. Добавьте MDX-контент ниже frontmatter: описание, ссылки, особенности —
   только то, что подтверждено источниками.
5. По возможности добавьте английскую версию в `src/data/centers_i18n/en/`
   с тем же именем файла.

Минимальный пример:

```mdx
---
title: Название центра
type: Зарубежный
category: Татарский
source: https://example.com/
location:
  country: Казахстан
  region: Карагандинская область
  city: Караганда
---

# Название центра

## Ссылки

- [Официальный сайт](https://example.com/)

## Особенности

- Короткие подтверждённые факты

## О центре

Нейтральное описание с проверяемой информацией.

## Источники

- [Название источника](https://example.com/)
```

Структура заголовков внутри карточки свободная, но держитесь принятого в
проекте порядка: `Контакты`, `Ссылки`, `Особенности`, `О центре`,
`Источники`. Так карточки читаются одинаково.

## Как менять существующую информацию

- Меняйте только поля и текст, которые действительно устарели или ошибочны.
- Не переименовывайте `tbk-*` файл.
- Не удаляйте информацию без причины; если данные устарели, замените их
  на подтверждённые.
- При изменении `title`, `summary`, `location`, `source`, `type` или
  `category` убедитесь, что источник подтверждает правку.
- Сохраняйте одинаковый фактический смысл между исходным и переведённым
  файлами.
- Центр закрылся? Не удаляйте файл молча — откройте issue или опишите это
  в PR со ссылкой на подтверждение, решение принимает мейнтейнер.

## Схема полей центра

Схема определена в [`src/content.config.ts`](./src/content.config.ts) через Zod
и помечена `.strict()`: **лишнее поле во frontmatter уронит сборку**.

| Поле | Тип | Обяз. | Примечание |
| --- | --- | --- | --- |
| `title` | строка | да | Непустая |
| `type` | enum | нет | См. [типы](#категории-и-типы) |
| `category` | enum | нет | См. [категории](#категории-и-типы) |
| `source` | URL | нет | Должен быть валидным URL |
| `summary` | строка | нет | Краткое описание |
| `pubDate` | строка | нет | Дата |
| `location` | объект | нет | См. ниже |

Поля `location` (все необязательные, объект тоже `.strict()`):

- `country`
- `region`
- `city`
- `flag`

## Категории и типы

Отдельного поля `tags` у центров нет. Группировка идёт через `category` и
`type`, оба заданы как Zod enum.

Разрешённые `category`:

- `Татарский`
- `Татаро-Башкирский`
- `Башкирский`
- `Крымотатарский`

Разрешённые `type`:

- `Регион РФ`
- `Зарубежный`
- `Онлайн`

Значения хранятся **по-русски в обеих локалях** — в английских карточках они
тоже пишутся кириллицей, перевод происходит на уровне интерфейса. Не
переводите их в frontmatter.

Не добавляйте новые категории или типы прямо в MDX. Нужна новая категория —
сначала обсудите в issue: меняется схема и логика фильтров в интерфейсе.

## Другие коллекции контента

Кроме центров в `src/data/` есть коллекции со своими схемами
(все `.strict()`, см. `src/content.config.ts`):

- `posts/` — редакционные посты. Обязательны `title`, `description`,
  `pubDate`, `author`, `category`; `tags` — массив, `ogImage` — необязательно.
- `projects/` — проекты и бизнесы. Обязательны `title`, `description`,
  `category` из набора `Общепит`, `Бизнес`, `Медиа`, `Образование`.
- `thanks/` — благодарности. Все поля необязательные: `name`, `instagram`,
  `telegram`, `social`, `sortOrder`.

Правила по источникам, нейтральному тону и приватности действуют и здесь.

## Переводы интерфейса

Строки интерфейса лежат в [`src/i18n/locales/ru.ts`](./src/i18n/locales/ru.ts)
и [`src/i18n/locales/en.ts`](./src/i18n/locales/en.ts). Это плоские словари
`Record<string, string>` с ключами через точку.

Добавляя UI-текст:

1. Добавьте **одинаковый ключ** в оба файла. Если ключа нет в `en`,
   `useTranslations` подставит русский текст — на сайте появится смешанный язык.
2. Используйте существующее пространство имён: `nav.*`, `list.*`, `detail.*`,
   `copy.*`, `feedback.*`, `menu.*`.
3. В компонентах — `useTranslations(locale)` и `t("key.name")`.
4. Не оставляйте видимый пользователю текст захардкоженным.

Подстановка значений — через `{token}`:

```ts
"list.found": "Найдено {count} центров",
```

```astro
{t("list.found", { count: centers.length })}
```

Локали и хелперы (`localizePath`, `getSwitcherHref`, `defaultLocale`) — в
[`src/i18n/index.ts`](./src/i18n/index.ts). Русский — локаль по умолчанию и
отдаётся без префикса, английский — по `/en/`. Внутренние ссылки строите через
`localizePath(locale, href)` — не собирайте пути вручную.

## Проверка перед PR

Для обычной правки контента достаточно внимательно перечитать изменённые
`.mdx` файлы. Если менялись схема, frontmatter, маршруты или локализация:

```bash
bunx astro sync    # проверяет frontmatter по схемам коллекций
```

Это быстрый способ поймать нарушения схемы — именно они чаще всего ломают
сборку.

Полную сборку запускайте, когда изменение затрагивает маршруты, Astro config,
интеграции или общую логику данных:

```bash
bun run build      # полная статическая сборка
bun run preview    # посмотреть собранный сайт
```

Чек-лист перед отправкой:

- [ ] `.mdx` проходит `bunx astro sync` без ошибок схемы;
- [ ] нет лишних полей во frontmatter;
- [ ] у фактических правок есть ссылка на источник;
- [ ] `tbk-*` имена файлов не переименованы;
- [ ] новые UI-ключи добавлены в `ru.ts` **и** `en.ts`;
- [ ] в диффе нет `dist/`, `.astro/`, `node_modules/`, `.env`, `package.json`
      с новой версией;
- [ ] PR посвящён одной теме.

## Ревью и что будет дальше

Проект ведёт один мейнтейнер, поэтому ответ может занять несколько дней —
это нормально, напоминание комментарием в PR уместно.

Что смотрят на ревью: проверяемость источника, соответствие схеме,
нейтральность формулировок, сохранность slug и узость диффа.

После мержа изменение попадает на `tatarverse.cc` при следующем деплое на
Cloudflare Pages. Версию релиза и деплой мейнтейнер делает сам.

## Частые проблемы

**Сборка падает с ошибкой схемы коллекции.** Скорее всего во frontmatter есть
поле, которого нет в схеме, либо значение `category`/`type` не из enum.
Схема `.strict()` — сверьтесь с [таблицей полей](#схема-полей-центра).

**`source` не проходит валидацию.** Нужен полный URL со схемой:
`https://example.com/`, а не `example.com`.

**На английской странице появился русский текст.** Ключ есть в `ru.ts`, но
отсутствует в `en.ts` — сработал фолбэк на локаль по умолчанию.

**`bun install` падает.** Проверьте версию Bun (`bun -v`, нужна 1.3+).
Как крайняя мера: удалите `node_modules` и поставьте заново.

**`git push` отклонён с сообщением про release commit.** У вас активен
хук `pre-push`. В форке он не нужен: `RELEASE_BUMP_SKIP=1 git push`.

**Ваш PR конфликтует с `main`.** См.
[синхронизацию форка](#работа-с-ветками-и-синхронизация-форка).
